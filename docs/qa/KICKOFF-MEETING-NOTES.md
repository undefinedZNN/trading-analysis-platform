## 3️⃣ 架构和代码讲解

### 系统架构概览

```
┌─────────────────────────────────────────────────────────────┐
│                    回测框架架构                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │
│  │   M1: 数据   │  │  M2: 执行    │  │  M3: 协调    │     │
│  │   Data Layer │  │  Execution   │  │ Orchestration│     │
│  └──────────────┘  └──────────────┘  └──────────────┘     │
│         │                  │                  │            │
│         └──────────────────┴──────────────────┘            │
│                           │                                │
│                  ┌──────────────┐                          │
│                  │  M4: 测试    │                          │
│                  │  Testing     │                          │
│                  └──────────────┘                          │
└─────────────────────────────────────────────────────────────┘
```

### M1 数据层

**职责**: 数据加载、转换、特征计算、事件分发

**关键组件**:
- `DataProvider`: 多格式数据源 (Parquet/CSV/JSON)
- `TimeframeAdapter`: K线聚合和时间转换
- `FeatureRegistry`: 特征注册和依赖管理
- `EventBus`: 事件发布/订阅和背压控制

**测试重点**:
- 数据加载准确性
- 时间聚合正确性
- 事件顺序保证
- 性能和内存使用

---

### M2 执行层

**职责**: 策略执行、风控、订单撮合、账本管理

**关键组件**:
- `StrategySandbox`: 策略隔离执行
- `RiskEngine`: 风控规则和强制平仓
- `ExecutionEngine`: 订单撮合和滑点模拟
- `LedgerService`: 资金和持仓管理

**测试重点**:
- 策略隔离和安全性
- 风控规则准确性
- 订单执行正确性
- 资金计算精度

---

### M3 协调层

**职责**: 流程编排、状态管理、快照恢复、结果分析

**关键组件**:
- `Orchestrator`: 整体流程协调
- `SnapshotManager`: 状态快照和恢复
- `Analytics`: 性能指标计算和报告生成

**测试重点**:
- 状态机转换正确性
- 快照一致性
- 指标计算准确性
- 端到端集成

---

## 4️⃣ 工具和流程培训

### 测试工具栈

```yaml
测试管理: GitHub Projects / Jira
缺陷跟踪: GitHub Issues
测试框架: Jest
性能测试: k6, Artillery
监控工具: Prometheus, Grafana (可选)
CI/CD: GitHub Actions
文档: Markdown (Git版本控制)
沟通: Slack #qa-testing
```

### 缺陷跟踪流程

```
1. 发现缺陷
   ↓
2. 在GitHub Issues创建缺陷
   - 标题: [模块] 简短描述
   - 标签: bug, priority-px
   - 内容: 步骤/预期/实际/截图
   ↓
3. QA Lead评审优先级
   ↓
4. 分配给开发人员
   ↓
5. 开发修复并提交PR
   ↓
6. QA验证修复
   ↓
7. 验证通过 → 关闭Issue
   验证失败 → 重新打开
```

### 缺陷优先级定义

- **P0 (Blocker)**: 核心功能完全不可用，立即修复
- **P1 (Critical)**: 严重影响使用，1天内修复
- **P2 (Major)**: 影响使用但有替代方案，1周内修复
- **P3 (Minor)**: 轻微影响，计划修复
- **P4 (Trivial)**: 建议改进，可选修复

### Q3: 如何处理已知的TypeScript错误？

**A**:
- 已知问题: Events模块有455个TypeScript编译错误

- 策略: 通过集成测试验证功能，跳过Events单元测试
- 文档: backend/TYPESCRIPT_FIX_FINAL_REPORT_V2.md

**决定**: 不阻塞测试，记录为已知问题

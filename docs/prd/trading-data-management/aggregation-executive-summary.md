# 交易数据多时间周期聚合 - 执行摘要

## 📋 需求概述

用户导入的原始交易数据（如1秒、1分钟级别）需要自动聚合成多种时间周期（1分钟、5分钟、15分钟、30分钟、1小时、1天、1周、1月），以减少高维度数据查询时的计算和IO开销。

**当前痛点**：
- ❌ 每次查询日线/周线数据都需要从分钟级数据实时聚合
- ❌ 大数据集聚合耗时2-5秒，影响用户体验
- ❌ 重复计算浪费CPU资源

**目标收益**：
- ✅ 查询响应时间从2-5秒降低到50ms以内（**40-100倍提升**）
- ✅ 减少90%+的IO读取量
- ✅ 降低CPU计算压力

---

## 🎯 推荐方案

### 方案名称：**混合预聚合策略（Hot Aggregation + On-Demand）**

### 核心思路
- **预聚合常用粒度**：1小时、1天（默认），5分钟、15分钟、30分钟、1周（可选）
- **按需聚合罕见粒度**：自定义或非标准时间粒度
- **增量更新**：追加数据时仅聚合新增部分

### 技术实现
1. **数据库设计**：新增2张表
   - `dataset_aggregations`：聚合结果元数据
   - `aggregation_tasks`：聚合任务追踪

2. **存储结构**：
   ```
   storage/datasets/
     └── binance/
         └── BTC_USDT/
             ├── 1m/           # 原始数据
             │   └── batch_1.parquet
             ├── 1h/           # 预聚合：小时
             │   └── agg_1h_from_1m.parquet
             └── 1d/           # 预聚合：日线
                 └── agg_1d_from_1m.parquet
   ```

3. **查询路由**：自动选择最优数据源
   ```typescript
   // 优先级：预聚合 > 实时聚合
   if (预聚合数据存在) {
     直接读取预聚合Parquet
   } else {
     实时聚合 + 可选缓存
   }
   ```

## 📊 性能与成本评估

### 性能提升（预估）

| 场景 | 当前方案 | 预聚合方案 | 提升倍数 |
|-----|---------|-----------|---------|
| 查询1年日线数据 | 2-5秒 | 50ms | **40-100x** |
| 查询1月小时数据 | 1-2秒 | 30ms | **33-66x** |
| 回测加载数据 | 按需实时聚合 | 直接读取 | **10-50x** |

### 存储成本

| 预聚合粒度 | 数据量占比 | 存储增长 |
|----------|----------|---------|
| 5分钟（5m） | ~20% | +20% |
| 1小时（1h） | ~1.7% | +1.7% |
| **总计（5m+1h）** | **~21.7%** | **约3-5%**（压缩后） |

**说明**：由于Parquet高效压缩，实际存储增长约为理论值的15-25%。

**结论**：以3-5%的存储空间换取40-100倍的查询性能提升，**性价比极高**。

### 聚合计算成本

| 数据规模 | 聚合粒度 | 预估耗时 |
|---------|---------|---------|
| 1个月 1秒数据 | 1分钟 | ~30秒 |
| 1个月 1秒数据 | 1小时 | ~20秒 |
| 1年 1分钟数据 | 1小时 | ~10秒 |
| 1年 1分钟数据 | 1天 | ~5秒 |

**结论**：聚合计算为一次性成本，相比长期重复的实时聚合，整体收益显著。

## 🚀 快速决策指南

### 需要决策的问题

#### 1. 默认预聚合粒度
**推荐**：`5m`（5分钟）、`1h`（1小时）

**理由**：
- 覆盖80%以上的常见查询场景（日内策略常用5分钟，日内到中期常用1小时）
- 存储增长约3-5%
- 可根据实际使用情况后续调整

**可选**：允许用户在导入时勾选其他粒度（15m、30m、1d、1M）

#### 2. 自动聚合触发时机
**推荐**：导入完成后自动触发（可配置关闭）

**理由**：
- 用户无感知，体验最佳
- 异步执行，不阻塞导入完成响应

**配置**：在数据集设置中提供开关

#### 3. 聚合任务优先级
**推荐**：低优先级后台任务

**理由**：
- 不应影响导入任务和查询性能
- 可利用闲时资源

## 🔍 技术细节速查

### 聚合SQL示例（DuckDB）

```sql
-- 从1分钟数据聚合到1小时
WITH bucketed AS (
  SELECT 
    *,
    CAST(FLOOR(epoch(timestamp) / 3600) * 3600 AS BIGINT) AS bucket
  FROM read_parquet('storage/datasets/binance/BTC_USDT/1m/**/*.parquet')
  WHERE timestamp BETWEEN '2024-01-01' AND '2024-12-31'
)
SELECT
  to_timestamp(bucket) AS timestamp,
  arg_min(open, timestamp) AS open,    -- 桶内最早的open
  max(high) AS high,                   -- 桶内最高价
  min(low) AS low,                     -- 桶内最低价
  arg_max(close, timestamp) AS close,  -- 桶内最晚的close
  sum(volume) AS volume                -- 桶内成交量累加
FROM bucketed
GROUP BY bucket
ORDER BY bucket
```

## ⚠️ 关键风险与缓解

| 风险 | 影响 | 缓解措施 |
|-----|------|---------|
| 聚合任务失败 | 预聚合数据不可用 | 降级到实时聚合，提供重试功能 |
| 存储空间不足 | 聚合任务失败 | 监控存储使用率，提前告警 |
| 追加写入时聚合冲突 | 数据不一致 | 使用数据库锁，序列化聚合任务 |
| 聚合计算资源占用 | 影响在线查询 | 限制并发聚合任务数，使用后台队列 |
